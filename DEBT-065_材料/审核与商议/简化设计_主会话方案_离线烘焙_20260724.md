# 简化设计(主会话方案):离线烘焙早退表 —— DEBT-065 第四轮

> 写于等 PlusAI 深度研究商议期间,供与 PlusAI 方案 + codex 三审根因三方对照。
> 用户 2026-07-24 拍板"先商议设计再修"(三轮审核逐层挖更深,疑设计过重)。

## 一、三轮漏洞的根因归类(不是四个独立 bug,是一类病)

| 漏洞 | 根因 |
|---|---|
| 身份可伪造(专用 slot/channel 标记≠来源证明) | **runtime 组装判据**:验证器在运行时从事实流里"认"身份,认的依据只能是字符串标记,而事实流是可被填充的 |
| 真实链路断路(节点属性 vs 查询字段不匹配,恒关闭) | **多跳运输**:资产经 loader→KG→retriever→validator 四跳,任一跳字段对不上就断,且断了是静默的 |
| 版本非精确(字典序 latest、绑包名非资产版本) | **runtime 版本冻结**:三资产各自在运行时选版本,"同一冻结选择"无法在 runtime 证明 |
| 卡值≠授权目标可判错 NA | **runtime 组装**:授权目标与卡实际组件值在运行时才凑到一起,凑的时候没交叉校验 |
| 单测伪造掩盖断路(躲过 104 测试) | **runtime 判据只能用构造输入测**:构造的输入 ≠ 真实链路产出,伪造属性天然掩盖断路 |

**一句话根因:把判据放在 runtime 组装,证明面就等于整条运输链 × 整个事实流,不可能靠字符串标记和单测封住。**

## 二、简化方案:把判据从 runtime 挪到离线烘焙

**核心**:早退决策在**离线生成阶段**算好,产出一张确定性表;runtime 只查表。

### 烘焙(离线,准备阶段)

输入(全部是离线确定的权威产物):
- W0 worldgen 产物:每 fragment 的 component_type(生成时的确定事实,不经 KG)
- 类型格:5 叶 + 10 排斥对
- 精确目标授权表:逐卡目标叶型(专员裁定)
- 卡包(rule_cards)

烘焙逻辑(**所有校验都在这里做,离线可充分验证**):对每个 `(rule_card_id, fragment_id)`,判定是否早退——卡有有效授权 ∧ 卡唯一组件值==授权目标 ∧ fragment 身份唯一且为叶 ∧ (目标, 身份) ∈ 排斥对。产出稀疏表(只存 early_exit=true 的条目,约 4,532 条):

```json
{ "anchor": {"pool_seed": "...", "rulecard_bundle_id": "...", "lattice_version": "...", "authorization_version": "..."},
  "entries": [{"rule_card_id": "...", "fragment_id": "...", "target_leaf": "...", "identity_leaf": "...", "reason": "provably_disjoint"}] }
```

### runtime(validator)

```
早退 ⟺ (card.rule_card_id, scope_fid) ∈ 烘焙表 且 表锚 == 当前批锚
```
**没有身份组装、没有版本选择、没有指纹校验、没有多跳运输**——只有一次查表 + 一次锚校验。

## 三、为什么这能封住三轮的全部漏洞

- **身份伪造**:runtime 不再"认"身份;身份在离线从 W0 产物直接读,事实流填什么都不影响。
- **链路断路**:运输从四跳降到一跳(表随批产物/rule_slice 带入);断了就是表缺失 → 保守全不早退(显式可见,不是静默恒关闭)。
- **版本非精确**:表自带四锚(池/卡包/类型格/授权表版本),runtime 只做一次"表锚==批锚"比对——同源是表的属性,不是 runtime 拼出来的。
- **卡值≠目标**:烘焙时交叉校验 `cvals == {target}`,不满足则该卡根本不进表。
- **单测伪造掩盖**:表是离线产物,可用**真实 30 栋数据全量验**(每条早退可追溯到 W0 身份 + 卡值 + 排斥对),不依赖构造输入;且表可 diff/审计(人可读)。

## 四、代价与风险

- 表规模:稀疏存储约 4.5k 条,可接受;每次换池/换卡包需重烘焙(和重锚批同频,本来就要重跑)。
- 灵活性下降:runtime 不能"临场推断"——但这正是我们要的(判据不该临场推断)。
- 烘焙器本身要正确:但它是**离线、可全量验证、可人读审计**的单点,比四组件 runtime 组装的证明面小一个数量级。
- 需确认:验证器拿到烘焙表的通道(随 rule_slice policy 带入 or 批产物路径),仍是一跳且断了显式。
