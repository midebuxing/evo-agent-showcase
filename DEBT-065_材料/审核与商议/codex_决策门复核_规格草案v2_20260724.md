## 新设计重点复核

### 1. §2.5 哈希绑定与“失效条目跳过”

“卡改动后该条目失效、只跳过条目”本身是**安全的保守退化**：只会减少结构 NA，不会产生未证成 NA，可以保留。

但当前有三个阻断：

- 红线 7 把“授权哈希失配”列为加载 hard-fail，[v2:29](/C:/dell_vs/5993/团队文档/我的笔记/spec草案_DEBT065类型格与授权状态轴_v2_20260724.md:29)；§2.5 又规定同一失配只警告并跳过，[v2:93](/C:/dell_vs/5993/团队文档/我的笔记/spec草案_DEBT065类型格与授权状态轴_v2_20260724.md:93)。两条不能同时实现。
- 没有定义 `card_content_sha256` 究竟哈希原始 `rule_cards.json` 单卡对象，还是 KG 重建后的 `RuleCardDTO`。现有 builder 会排序多个子数组，[pack_builder.py:500](/C:/dell_vs/5993/agent_v1/src/evo_agent_baseline/retrieval/pack_builder.py:500)，再重建 DTO，[pack_builder.py:663](/C:/dell_vs/5993/agent_v1/src/evo_agent_baseline/retrieval/pack_builder.py:663)，两种口径不能靠实现者猜。
- `entries` 没有唯一性规则。两个同卡、同哈希但不同目标集的有效条目，究竟取首条、并集还是 hard-fail，结果会影响 NA。

建议定死为：

- 资产结构损坏、重复有效条目、非法目标/证据、非法哈希格式：ingest hard-fail。
- 结构合法但卡不存在或独立计算的卡指纹不匹配：标记 `stale_card_binding`，仅该条目失效。
- runtime 选定资产整体缺席：组件结构早退整体关闭。
- 明确一个命名哈希 profile，并规定 `rule_card_id + authoring_revision + interpretation_revision + card_content_sha256` 是否全部必须相等；最好再加顶层 `rulecard_bundle_id`。
- 第一波有效目标应校验为非空且 `target_types ⊆ lattice.leaf_types`，而不只是词表值域。

### 2. §3.0 identity provenance

方向正确，但目前“专属 provenance 标记”仍只是散文。现有 `FactAtom.provenance` 是任意字典，[contracts.py:373-409](/C:/dell_vs/5993/agent_v1/src/evo_agent_baseline/contracts.py:373)，无法由规格判断什么才是合法身份事实。

至少要定死：

- 保留的 slot/channel 名和 schema；
- `fragment_id`、`component_id`、原始 `component_type`、规范值；
- `alias_mapping_version` 与 `alias_mapping_snapshot_sha256`；
- validator 必须把 provenance 哈希与 lattice 快照相等作为消费前提；
- “唯一”是恰一条原始 `Fragment→Component` 来源关系，不是规范值去重后只剩一个。

最后一点很重要：当前查询允许同一 fragment 因多条关系返回多行，[queries.py:31-36](/C:/dell_vs/5993/agent_v1/src/evo_agent_baseline/kg/queries.py:31)，而现有 enrich 路径按 fragment 建字典会后写覆盖，[fact_retriever.py:496-502](/C:/dell_vs/5993/agent_v1/src/evo_agent_baseline/retrieval/fact_retriever.py:496)。新通道不得复用这种 last-write-wins 形态。

### 3. §3.2 第 4 条的子集语义

**仅做值集合子集不足以证明该触发器来源项获正向授权。**

反例：卡授权目标集为 `{A,B}`，某触发器限定 A，但 A 在该触发器上只是跨组件证据宿主；求值 fragment 身份为 B。此时 `A ⊆ {A,B}` 成立，且 A、B disjoint，于是触发器被错误判 NA。

当前 397 卡暂不实例化这个漏洞——现语料每卡只使用一个组件类型值，[vocab_cards.md:62](/C:/dell_vs/5993/杂物箱/文件包/DEBT-065_修复周期材料_20260724/勘察/vocab_cards.md:62)。但 schema 和授权资产都允许多目标，因此规格级漏洞仍存在。

二选一即可关闭：

1. 推荐：授权资产增加逐源项授权，触发器必须命中明确的 `condition_id/slot_ref_id` 授权记录；或
2. 实验室最小案：v1 强制每个有效条目恰一个目标类型，并把“每卡单组件值”设为加载不变量，未来多目标另升版。

现有 `evidence` 示例只有 `slot_ref_id`，[v2:80-84](/C:/dell_vs/5993/团队文档/我的笔记/spec草案_DEBT065类型格与授权状态轴_v2_20260724.md:80)，还需补 `condition_id` 形态和“证据对象即获授权来源项”的规范语义。

### 4. 资产版本与二分测试

“固定版本别名映射”没有给出确切 version/bundle 选择规则。现行查询是 `ORDER BY version DESC LIMIT 1`，[queries.py:49-53](/C:/dell_vs/5993/agent_v1/src/evo_agent_baseline/kg/queries.py:49)、[queries.py:168-179](/C:/dell_vs/5993/agent_v1/src/evo_agent_baseline/kg/queries.py:168)；这既不是精确选择，`v10/v9` 时还可能产生字典序问题。应规定三项资产版本在一次 run 开始时冻结，并按精确键查询，缺失不得回落其他版本。

§2.3-⑥也要拆成两个断言：

- `leaf_types ∪ non_leaf_types == component_type_key` 词表全域，且二者不交；
- W0 **实际生成计划**中的原始类型必须全部有 alias，映射结果必须全部落入上述二分。

现行生成计划是 11 种，[generator.py:303-359](/C:/dell_vs/5993/agent_v1/src/workflow_engine/worldgen/generator.py:303)，11 种均有映射；registry 则有 19 种，其中 8 种未映射，[w0_ontology.md:15-39](/C:/dell_vs/5993/杂物箱/文件包/DEBT-065_修复周期材料_20260724/勘察/w0_ontology.md:15)。若坚持检查 registry 19 条，就必须再显式分类“可生成/休眠且未映射”，禁止静默丢弃。

## 终判与剩余阻断
