# baseline 收官·消费者验收契约(提案 v0.1)

> **状态**:提案,待用户审批。本文把用户 2026-07-18 定的收官标准"消费者优雅可用无明显缺陷"从主观判断**操作化为可证伪判据**,防止再次出现"拿机器可核属性代答人读体验"(2026-07-23 教训)。
> **权威边界**:本契约**定义验收口径**,不改任何冻结规格;凡涉及修改报告契约 v3 骨架(设计规格 v0.4 §7.4)的动作,须先单独修订该 spec 再落码(spec→code 单向红线)。
> **来源**:codex(gpt-5.6-sol)决策门商议 + 两轮实测审计(消费者动线 44 坑 / 语义审计 11.6% 严重错误率)。

## 0. 收官口径(用户原文 + 本契约的操作化)

用户 2026-07-18:「验收标准 = 消费者优雅可用无明显缺陷(一键跑批→产物完整可信→阅卷可信→数字可引),有坑即未收官」。

**"有坑即未收官"的可操作边界**(codex 裁定,防扩成无限产品需求):收官阻断项**只包括五类**——
1. 会误导判定或证据含义(**正确性缺陷**);
2. 无法在合理时间找到主要结论;
3. 大量机械重复;
4. 引用跨批不可追;
5. 正式入口或复现锚不清楚。

分页 UI、搜索、交互仪表盘、多格式导出等**一律写入论文 limitation,不进本轮**。

## 2. 四道验收硬门(全过才允许说"消费者优雅")

### A. 结构与密度门(脚本 `check_report_usability.py`,待建)
- 主视图非空行 ≤180/份;完整台账可折叠或单独落盘、不计主视图。
- 主视图"结论/原因组/建议动作/证据入口"行占比 ≥20%。
- 主视图 24 位运行期哈希 = 0;详细台账与映射中保留 100%。
- 规范化完全重复复核句 = 0;除表头/免责/引用外规范化重复行率 ≤5%。
- 未解释中英混排分析点 ≤2%(代码标识/法规原文/正式术语不计)。
- Markdown 标题层级/表格列数/内部链接检查:错误 0。

### B. 权威完整性门(脚本 `check_report_authority.py`,✅ 已建并跑出基线)
- 从 `closure_validation_result.json` 重算 total/open/blocked/closed/satisfied/violated/unknown/NA:逐字段完全相等。→ **G 批 20/20 全符**。
- 每个 O-R 绑定的 R = 该 O 的 `source_rule_card_id`;每个 O-F 绑定的 F ∈ 该 O 的 `evidence_fact_ids`:100%。→ **G 批 640/643 = 99.5%**,LOWRISE-0030 三点 O 错位一位(第十轮记录,释义审计漏掉的结构性错绑)。
- (待步骤 2 补)主报告每个聚合组展开后的义务集合与权威结果集合相等;每个 display_ref 唯一且能回到一个原始义务:100%。

### C. 叙述语义可信门(人工语义审计,现有闸做不到)
- 全部模型点由一名审查者逐点对照绑定的 O/R/F;分层随机 20% 第二名盲审复核。
- 严重错误(规则含义错位/事实反转/错误对象/错误阈值/状态改写)**必须 = 0**;轻微术语错误率 ≤2%;双人样本 Cohen's κ ≥0.80。
- **处置进程(2026-07-23)**:初测 353 可核点 41 严重 = 11.6%。option (a)(提示词不复述规则,H 批实证)把真·规则转译 25%→6%、严重错释义按构造大幅降。**残留未归零** → 按 codex 止损规则走兜底 (ii):报告分析节加**确定性权威声明**(规则内容以「法规引用与证据」权威条文为准、模型转述仅供参考),残留不能静默误导。**门状态 = 「未严格通过(0 错误未达),已降 76%+确定性兜底声明+权威条文邻接,列 documented limitation」**——非绿,是"已知有界限制下收口"。严格绿需 step 3b 确定性规则内容重构。

### D. 盲用任务门(3 名未参与实现者,需人力)
- 每人读分层选出的 6 份报告,答固定五题(见接触面 4)。
- 总正确率 ≥90%;`allow_stop` 正确率 100%;中位 ≤5 分钟/份、P90 ≤8 分钟;"找不到证据入口"= 0;盲审者不得事先受作者口头培训。

## 3. 三个安全边界(呈现改造不得污染判定层)

越界即违红线:①改 validator/义务派生/reason_code/identity/dedupe;②为缩短报告而过滤闭包输入或改状态;③让 LLM 决定计数/分组成员/风险等级/`allow_stop`;④让 eval 结果回流 agent runtime;⑤用 display_ref 替代内部 obligation identity。

**安全证明分两层**(改造后须重跑,证明对象变了):
1. 离线重渲染:用原 `closure_validation_result + accepted_payload` 重渲染 20 栋,除报告及新展示映射外所有既有 JSON 逐字节不变。
2. 全链不变性:固定 FactPack/RuleSlice 重跑 20 栋,`allow_stop`/closure summary 全字段/逐义务语义键/eval metrics 与真实分母/leakage 全部与冻结权威一致(报告文本 hash 允许变)。

## 4. 已识别的三个 spec 授权点(动代码前须先改 spec)

1. **移出/折叠大表**:设计规格 v0.4 §7.4 冻结"程序骨架至少含未闭合项表、禁 LLM 删/重排骨架"。低风险路=Markdown `<details>` 折叠但完整表留同文件;更干净路=修订 §7.4 定义"主报告聚合表+完整确定性详细台账为同一逻辑工件"。
2. **display_ref 展示编号**:纯展示层,由 `canonical_identity_hash/dedupe_key` 确定性派生、不含 `run_id`、不成为 identity-v5 新键、每报告落 `display_ref→obligation_id→canonical_identity_hash` 映射。原始 JSON 保留完整 `obligation_id`。**不改 identity-v5**。
3. **复核提示按规则卡程序聚合**:分组键 ⊇ `(rule_card_id, closure/satisfaction category, reason_code, target scope)`,每组显示数量+目标摘要+详细台账链接。**聚合与计数全程序完成,不让 LLM 决定分组成员或计数**(不破防编造设计)。

## 5. 阻断项优先级(codex 裁定)

**最值得优先的不是折叠表格,而是先查清并堵住 C 门的语义错位**(11.6% 严重错误已是可信度缺陷,答辩随机核一条就会追问"100% 采纳到底验证了什么")。修复方向:既然权威原文已在"法规辑录"确定性渲染,**让模型不复述规则要求、只写缺口与复核动作,规则内容一律指向 [Rn]**;若自由释义仍不可稳定验证,则程序展示原始短引文、模型只描述 gap。**不走提示词加正例老路**(EXP-015 C→D 已证净负面且脆弱)。
