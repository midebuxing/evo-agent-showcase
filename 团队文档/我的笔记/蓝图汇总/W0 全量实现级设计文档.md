> **Pipeline 定位：W0 静态资源 → W1 生成规则 → W2+ Runtime**

## W0. Generation Resources (生成资源层)

### 1. 设计原则与法规本体边界 (引自 a4 canonical slot universe 与 a5.md)

除了物理图谱与机理外，W0 还需要承接来自 `团队文档/技术团队文档/rulecard工程/answer/a4.md`（canonical slot universe / regulation-family coverage）和 `a5.md` 的法规边界与认识状态定义，这些是规范生成器业务分类的核心前提（Ontology）。本文所有 `a4` 引用均指这份 canonical slot 文档，不指 `pro-answer/a4.md` 的 System Prompt / Hooks 运行时控制文档。它规定了 17 张表的填充白名单，以及运行时数据打包的 Schema 包装盒。

#### 1.1 全量覆盖领域的业务范围 (Scope Domains)

W0 中 17 张表的数据填报，必须严格限制在 `团队文档/技术团队文档/rulecard工程/answer/a4.md` 划定的 5 大物理与技术领域内：

> **引自 a11.md §2.2 & canonical a4（团队文档/技术团队文档/rulecard工程/answer/a4.md）的业务边界约束**：
> 必须新增统一 condition/defect 语汇，至少覆盖：
>
> 1. structural/external defects (结构安全与外墙)
> 2. drainage fault/defect (排水管网系统)
> 3. UBW / subdivided-unit signs (僭建与改建)
> 4. fire-safety component deficiency (消防安全物理缺陷)
> 5. technical measurement taxonomy (技术验证与结构评估)
>
> **关于排除项的硬性规定 (引自 a11.md §1.6)**：
> canonical a4 的 world ontology baseline 已经明确：纯 world truth 直接支持的是 building/component/defect/measurement/drainage/repair/verification；procedure / artifact / supervision 应独立 sidecar 承载。

#### 1.2 业务域、数据职能分组与 17 张表的关系

5 大业务域、§2 的 6 大资源域 + 1 项边界契约、17 张表之间是多对多关系，不是逐层细分关系。

§2.1 资产空间域、§2.7 Sidecar 边界契约，以及 §2.2 中的部分 material 资源，是域无关基础设施；5 个业务域共用同一组表。

§2.2 的 `defect_condition_taxonomy_registry`、§2.5 的 `mechanism_library_registry`、§2.4 的 `risk_derivation_registry` 属于表内多元：一张表里包含多个物理域的条目，按 component / condition 类型区分归属。

D5 技术测量域比较特殊：它由 §2.3 与 §2.6 的多张表共同构成；但这些表同时也是 D1–D4 的测量服务，既是业务域的一部分，也是跨域基础设施。

因此读者不应把 §2 的资源域/边界契约看作 5 大业务域的细分。两者是不同维度的切片：5 大业务域按“业务问题”切，§2 的分组按“数据职能”切，17 张表是这两个维度交叉后的工程落地。

几个关键观察：

1. **资产空间域是全域底座**：5 大业务域无一例外全部依赖它，因为所有物理世界都必须先有建筑、构件和位置。
2. **D5 技术验证的独特性**：它是唯一强依赖 `sampling_plan_registry`、`assessment_surrogate_registry` 和 `verification_test_registry` 这三张高阶算法表的领域，其他领域多为弱依赖或不涉及。
3. **D3 僭建是较轻的业务域**：它几乎不需要复杂的驱动/测量公式，更多依赖空间拓扑（有没有非法搭建物）和缺陷分类（是什么类型的违建）。
4. **`normative_projection_registry` 是唯一全 `●` 的表**：因为所有业务领域的法规绑定都必须经过它。

#### 1.3 W0 输出的认识论状态（World Truth + Normative Truth）

在 W0 层，系统生成的每一个案例（Latent Case）应至少包含以下两层核心认识状态（Epistemic States）：

1. **底层真实状态 (World Truth)**：系统全知，包括建筑环境、构件材料、缺陷形态、真实测量值。
2. **规范真实状态 (Normative Truth)**：由 `normative_projection_registry` 对 World Truth 做法规投影后的结果，包含触发的规则族、阈值阶段（如 `near_above`）与约束归类。

> **本版范围说明**：Evidence Topology / Observation Plan / Episode Intention 由后续调查员模拟层负责，本设计暂不纳入 W0。

#### 1.4 显式未知类型的分类 (Explicit Unknowns)

为了支持 Agent 的诊断推理，W0 的生成不能用通用的 `null` 来敷衍“不知道”。必须按照以下分类生成数据：

> **引自 a5.md 对未知类型的强制约束**：
> 这三种不要混成一个 `null`。我强制做成 typed state：
>
> * **`missing`**：真值存在，但当前没暴露。可能可从 KG 拿，也可能只能问人。
> * **`unknown_world`**：真值在这个世界里就没有被测到/没有 authoritative value。
> * **`conflict`**：两个或多个来源对同一 slot 给出不一致说法。
> * **`not_applicable`**：这个 slot 对当前 case 根本不适用。

#### 1.5 硬约束分类与失败策略
> 源：a12.md:1578 §9；a5.md:296 hard constraints

约束分类：`a5.md` 把 hard constraints 分为 **物理兼容约束** 与 **规范兼容约束**。`a12.md §9` 没有另设“类别”列，而是用 `优先级` 作为可执行分类：`P0` 包含 `C001`–`C006`,`C009`–`C012`,`C015`–`C020`,`C025`,`C026`；`P1` 包含 `C007`,`C008`,`C021`,`C022`；`P2` 包含 `C013`,`C014`；`P3` 包含 `C023`,`C024`。

失败处理：原文四档为 `P0: reject_or_resample`、`P1: repair_world_truth_geometry_or_state`、`P2: repair_measurement_rounding_or_bounds`、`P3: projection_fallback_to_unknown_or_not_applicable`。`P0` 输出形态是 reject / reject projection / resample；`P1` 输出形态是 clamp、recompute repair flag、recompute flag；`P2` 输出形态是 clamp、round/clamp；`P3` 输出形态是 clear rule_ids、resolve or unknown conflict，或 fallback 到 `unknown` / `not_applicable`。

### 2. 世界宇宙的六大资源域 + 一项边界契约 (基于 a11.md 的扩容分组逻辑)

最初的 W0 原型（Seed Spec）仅能生成单一的裂缝和剥落。为了支撑第 1 节划定的“全量法规边界”，`a11.md` 强制要求在资源引擎中扩充出六个资源域（Domain），并额外划出一项 Sidecar 边界契约。它们构成下文 17 张数据表矩阵的具体分组归类。

#### 2.1 资产空间域 (Asset / Scope / Location Domain)
必须从单一的病害点，上升到具备宏观几何拓扑的建筑世界。
* **对应注册表**：`building_template_registry`（建筑大类模板）、`component_type_registry`（构件字典）、`location_class_registry`（空间位置分类）、`coverage_relation_registry`（遮挡与视线覆盖关系）、`fragment_template_registry`（片段母题模板）。

#### 2.2 缺陷字典域 (Unified Defect / Condition Taxonomy Domain)
不能只管结构，必须将 5 大领域的物理破坏拉齐到一套统一的本体词汇下。
* **对应注册表**：`defect_condition_taxonomy_registry`（全量缺陷分类大表）、`material_system_registry`（材料系统属性表）。

#### 2.3 驱动测量域 (Drivers & Independent Measurement Domain)
引入让世界随时间腐化的隐变量（Latent Drivers），并且坚决将“物理损坏的真实尺寸”与“人类的测量工具与抽样方法”解耦。
* **对应注册表**：`latent_driver_registry`（隐变量环境先验表）、`technical_measurement_registry`（独立技术测量字典）、`sampling_plan_registry`（抽样比率与规则计划）。

#### 2.4 派生风险域 (Risk / Repair Derivation Domain)
世界不光要有物理病害，还必须能在底层自动推演出“是否触碰紧急危险红线”、“是否满足强制修缮门槛”。
* **对应注册表**：`risk_derivation_registry`（风险阈值派生表）、`repair_outcome_registry`（修缮结果验证表）。

#### 2.5 专门物理域（Specialized Physical Domains：drainage domain / UBW domain / fire-safety physical domain）
> 源：a11.md:127 §2.5

`a10` 还缺三类专门 domain：**drainage domain**（segment / connection / misconnection / blockage / location / risk / test subject）、**UBW domain**（unauthorized structure / alteration / status / subdivided-unit indicators）、**fire-safety physical domain**（物理 component deficiency 本体）。其中 `outstanding statutory upgrade` 这种 record-driven status 不应归 world core。

`mechanism_library_registry` 是承载这些专门物理域退化机理的核心 registry：它记录 applicable component types、required driver fields、output condition classes 与 `surrogate_id`，把 drainage / UBW / fire-safety 的物理状态生成接到 W0 的机理层。
* **对应注册表**：`mechanism_library_registry`（机理演化函数库）。

#### 2.6 高阶评估域 (Assessment & Verification Domain)
支持需要套用专业公式的高阶技术动作，例如拉拔测试的合格验证、混凝土芯样化验、结构性能折减率评估。
* **对应注册表**：`verification_test_registry`（验证测试模型表）、`assessment_surrogate_registry`（工程评估代理模型表）。

#### 2.7 Sidecar 边界契约 (Sidecar Boundary Contract)
划定物理引擎与行政文书引擎的鸿沟：明确规定哪些变量由 W0 负责生成，哪些文书流程（如报告签字、通知下发）踢给外部的 Sidecar 系统生成。

它不同于 2.1–2.6 的物理/技术数据域：前六个 domain 回答“生成什么物理真相”，本节回答“哪些不该由 W0 生成”，因此是生成边界的元规则。

* **对应注册表**：`sidecar_ownership_registry`（外挂归属定义表）、`normative_projection_registry`（规范投影与绑定的规则口）。

> 源：a12.md:1894 §14

#### 3.4 生成顺序与依赖
> 源：a12.md:1034 §7

`a12.md §7` 标题为“生成算法七段式规格”，但实际定义了 10 段生成函数，顺序如下：

| 顺序 | 函数名 | 功能 | 输入对象 | 输出对象 | 前置依赖 |
| ---- | ------ | ---- | -------- | -------- | -------- |
| 1 | `generate_building_world_bundle` | 生成 building / component / location / fragment 的基础 `WorldBundle` | `archetype_id`, `seed`, `config`, `registries` | `WorldBundle` | registry / building archetype 已准备 |

### 4. 架构评价与现状

* **`[D0] 多样性入口`**：多样性的源头完全依赖于各个注册表的规模、先验分布的设计、机理库的丰富度以及约束库的灵活性。这是实现全覆盖（Full-coverage）生成架构并避免写死 case 的唯一途径。*(来源：a12.md §1)*
* **工程现状 (`[CURRENT]`)**：
  * **Registry 模块结构**：`src/workflow_engine/worldgen/` 下已完成模块拆分，原 `framework.py` 已重构为 `hydration.py`（世界水化/装配）、`validation.py`（输出验证）、`profile_handlers.py`（场景模板）、`seed.py`（种子推导）四个独立模块，解决了先前两套并行 `_build_registry_bundle()` 的同步风险。`registry.py` 是目前唯一的 bundle 定义源，并在 `data/` 目录下输出 `registry_tables.v1.json` 作为审计快照。
  * **Registry 的实际角色（验证层 vs 生成层）**：`registry_bundle` 目前已接入 `validation.py` 的跨表约束校验（`registry_map` 查表，核查 world 输出是否合规），起到"验证约束"作用。但**生成层（`profile_handlers.py`）仍是 Python 硬码 template 驱动**：11 个 profile domain 的 scenario 构造全部写死在对应的 Python 函数中，并不从 registry 表动态采样，尚未实现真正的"配置驱动"生成。`registry_tables.v1.json` 是输出产物而非输入源，生成主流程不读取它。
  * **动态推演接口（Surrogate & Formula）挂载状态**：
    * **`surrogate_id`**：在 `registry.py` Schema 中作为字段预留，但全代码库无任何模块通过 `surrogate_id` 路由到物理计算函数。物理计算目前由 `physics_damage.py`、`physics_outcomes.py`、`physics_primitives.py`、`physics_sampling.py`、`physics_measurement.py` 五个模块直接以 Python 函数硬码实现，surrogate 路由尚未接驳。
    * **`formula`**：风险评估等表达式字符串（如 `"severity_index >= 0.85 or ..."`）已写入 Schema，但全代码库无任何解析器执行这些字符串，动态 expression evaluator 尚未实现。
  * **多样性组装现状（Seed vs Atomic）**：生成多样性目前依赖两个来源：`seed_worlds.v1.json`（4 个整块快照世界）和 `profile_handlers.py`（11 个 Python 硬码场景函数）。17 张原子表填充量严重不均，最稀疏的几张如下：`assessment_surrogate_registry`（1 条）、`measurement_surrogate_registry`（2 条）、`latent_driver_registry` / `risk_derivation_registry` / `repair_outcome_registry`（各 3 条）。后续核心任务是填满原子表，并将 `profile_handlers.py` 的硬码场景下沉为由 registry 驱动的纯动态组装。
