## 一、1a-0 解绑：`sidecar_rng` 种子脱离 `registry_bundle_hash`

### 改了什么

`agent_v1/src/workflow_engine/worldgen/validation.py`
（`run_worldgenerator_fullcoverage_framework_v2` 内）：

```python
# 旧
sidecar_rng = _random.Random(int(deterministic_key[:16], 16))
# 新（1a-0）
sidecar_rng = rng_domains.sub_rng(rng_domains.SIDECAR_BATCH, str(seed))
```

⚠️ 这行在 **1a-i′ 之后已整条删除**（批级流退役，见 §三）。
本节记的是它**作为独立一步被单独验过**的效应——那正是分步落地的全部意义。

新建 `agent_v1/src/workflow_engine/worldgen/rng_domains.py`：**域串登记表 ＋ 唯一构造入口**。
域串集中登记（1a-i 四条、1a-i′ 四条、1a-ii 一条 ＝ **9 条**；
1a-0 那条 `SIDECAR_BATCH` 在 1a-i′ 把批级流拆掉后**一并删除**——
留着它等于给「再造一条批级流」留个现成入口。删后重跑全池，23/23 逐字节不变，
证实它当时已是死常量），
**导入时自检唯一性**（撞名当场 `AssertionError`）——「两个消费点共用域串 ⇒ 退化成一条流」
是最阴的失败形态（键写错但测试全绿），故把它变成结构上不可能，而不是靠运行时断言。
`sub_rng()` 同时拒绝非 `str` 的键段（防「不小心把 index 传进来」，那正是要治的病换个地方复发）。

**只解流、不解锚**：`deterministic_key` / `registry_bundle_hash` 照旧计算、照旧写进
各 meta 与 cohort manifest。实测两侧 `deterministic_key` 均为 `923f9e48…afffd`，逐字节不变。

## 二、1a-i 四阶段子 rng：`generate_world_bundle` 的四个后置逐片段阶段

### 改了什么

`agent_v1/src/workflow_engine/worldgen/generator.py`，四个函数：

| 阶段 | 函数 | 域串 |
|---|---|---|
| S1 | `generate_coverage_relations` | `w2rng.coverage_relations.v1` |
| S2 | `generate_coverage_sampling_measurements` | `w2rng.coverage_sampling.v1` |
| S3 | `generate_technical_validation_measurements` | `w2rng.technical_validation.v1` |
| S4 | `generate_structural_assessment_measurements` | `w2rng.structural_assessment.v1` |

每个阶段在逐片段循环体内建 `sub_rng(域串, world_id, fragment.fragment_id)`；
S4 的子流建在**两个 guard（`mechanism` 非 active / `component` 缺失）之后**，
被跳过的片段不建无用子流。

**`rng` 形参一律删掉**（三线裁定④一致：甲）。删而非留，是让「不消费主 rng」
成为结构上不可能违反的事实——比任何 `rng.getstate()` 运行时断言都强，
后者反而要求函数继续收一个它不用的参数。四个函数改用
`*, world_id: str` **关键字必填**：任何按位置传 `rng` 的旧调用直接 `TypeError`，红即可见。
调用点 `generate_world_bundle` 四处改传 `world_id=world_id`
（`world_id` 含 seed，`building_id` 不含 ⇒ 只用 `building_id` 会让不同 seed 的池共享子流）。

### 🔴 一处对核清的订正：S4 的主 rng 消费点是 **7 处不是 2 处**

核清 §1.1 记 S4「主 rng 消费只有 2 处（:2431 / :2441）」。实读全函数体，
片段循环内还有 **5 处**：`:2247`（`_compute_inspected_area_ratio_per_fragment`）、
`:2364`（`_sample_rebar_type`）、`:2367`（`_sample_rebar_location`）、
`:2374`（`_sample_corrosion_loss_type`）、`:2382`（`_compute_rebar_section_loss_ratio_per_class`）
——都在 chain derive / 钢筋锈蚀分支里，核清那张表漏了。
全部在两个 guard 之后，故子流建在 guard 之后即可一次覆盖，改法不变。
**若照核清只改 2 处，剩下 5 处仍吃主 rng，隔离就是假的、而字节锚照样会绿**
（因为主 rng 在这一步之后再无消费者，位移体现不出来）。

### 字节锚结果（`--step 1a-i`，基线＝1a-0 后的池）

|---|---|
| **PASS** | **12 个须相同单元逐字节一致**，其中最关键的是 **`sidecar.entries` 19,090 行逐字节不变**（本步的锚）；另含 `buildings` / `components` / `locations` / `fragments` / `specialized_states` / `driver` / `mechanism` / `condition.core` / `repair_assessment.core` / `world.meta` |

### ⚠️ 一条实测到的**潜伏耦合**（官方线尾巴 1，本次关闭到「查实但未爆发」）

官方线说「四阶段 ⊥ sidecar」只 grep 过 sidecar 主循环入口、没逐行核完。我核完了：

- 通道**存在且只有一跳**：`measurements` → `populate_derived_flags` 回写
  `RepairAssessmentState` 四个 bool → sidecar 的 `_build_round6_hidden_state_for_fragment`
  读 `repair.repair_required` 造 `H.repair_need` → 三个 sidecar bool 槽的
  `conditional_formula` 消费 `H.repair_need`（实测：`procedure.supervision_representative.planned`
  / `procedure.repair.prescribed.started` / `artifact.proposal.repair`）。
- 本次**没有爆发**，原因查实：RAS 四个回写字段里，1a-i 只动了 **`verification_failed`（30/340）**，
  `repair_required` / `maintenance_required` / `safe_until_next_cycle` **一条都没变**；
  而 sidecar 从 RAS 只读 `repair_required`（＋非回写字段 `repair_quality_index`）。
- ⇒ **字节锚为真，但它不等于「两侧正交」**。将来任何让 `repair_required` 翻的改动
  （1b 的 fsp 解耦就直接动 `assessment_flags`）都可能把四阶段的位移传导进 sidecar，
  届时这条锚会红——**红了不是锚坏了，是这条通道终于发作**。

## 三、1a-i′ sidecar 槽级 ＋ combo 维子 rng

### 改了什么

`agent_v1/src/workflow_engine/worldgen/sidecar.py` 四个消费点（＋一条旧路径）：

| 消费点 | 域串 | 键 |
|---|---|---|
| 数值槽 `_sample_sidecar_facts_for_fragment` | `w2rng.sidecar.numeric.v1` | `(world_id, fragment_id, slot_id)` |
| 楼级 bool 槽 | `w2rng.sidecar.bool.building.v1` | `(world_id, slot_id)` |
| 片段级 bool 槽 | `w2rng.sidecar.bool.fragment.v1` | `(world_id, fragment_id, slot_id)` |
| **轴积槽** | `w2rng.sidecar.axis.v1` | `(world_id, slot_id, **规范化 combo**)` |
| 旧路径 `_sample_sidecar_bool_slots_for_fragment` | 同片段级 | 同键（与生产路径同流） |

规范化 combo ＝ `"|".join(f"{k}={v}" for k, v in sorted(combo.items()))`，让 dict 遍历序不进键。
**combo 维实测确有对象**：`sidecar_bool_slot_registry` 52 条里带轴积的 4 槽，
组合数 13 / 8 / 1 / 1，其中三个槽的轴含 `actor_role_key` —— #29 BA→BD 改的正是这个轴。

### 🔴 批级 sidecar 流整条退役（超出实施卡字面，但是它的必然结论）

四个点都改成槽级键之后，`_build_sidecar_runtime_bundle_for_buildings` 的 `rng` 形参
**在生产路径上一次都不被消费**。按裁定④同一条理由（死参＝「关键配置静默退化」那个 bug 族），
把 `rng` 从 sidecar 五个函数与 `validation.py` 一并删除，`sidecar_rng` 局部变量随之消失。

**这不是把 1a-0 撤销，而是把它结构化**——两者治的不是同一半：

| | 1a-0 解绑 | 1a-i′ 槽级化 |
|---|---|---|
| 治「改注册表 ⇒ 整批重掷」 | ✅ | ✅（更彻底：根本没有批级流） |
| 治「第 i 栋片段数一变 ⇒ 第 i+1..n 栋全部移位」 | ❌ **治不了** | ✅ |
| 治「加一个槽 ⇒ 同栋其余槽移位」 | ❌ | ✅ |

⇒ 1a-0 那一步的价值是**把解绑的效应单独量了出来**（33.2% → 0），
不是那行代码要永久留着。顺带消掉一处历史隐患：`rng=None → random.Random()`
（「仅供测试便利」的非确定性缺省）也一并没了，确定性从此是构造性的。

### 字节锚结果（`--step 1a-i-prime`，基线＝1a-i 后的池）

| **PASS** | **16 个须相同单元逐字节一致**，其中本步的锚是四阶段侧：**`measurements` 6,105 行 ＋ `coverage_relations` 340 行 ＋ `condition.derived_outcomes` ＋ `repair_assessment.writeback` 全部逐字节不变** |

## 四、1a-ii 片段模板选择稳定化

### 改了什么

`generator.py` 的 `_select_fragment_templates`：两处 `rng.shuffle` → **按稳定键排序取前 k**
（三线定稿的候选甲），`rng` 形参一并删除 ⇒ **本函数对主 rng 的消费归零**。

```python
def _template_key(t):
    return rng_domains.stable_sort_key(
        rng_domains.FRAGMENT_TEMPLATE_SELECT, world_id, t["fragment_template_id"])
pool      = sorted(primary,   key=_template_key)   # 原 rng.shuffle(pool)
remaining = sorted(remaining, key=_template_key)   # 原 rng.shuffle(remaining)
```

`rng_domains` 新增 `stable_sort_key(domain, *parts) -> bytes`（SHA-256，同一套域串登记与
str 校验）。它比 `sub_rng` 更强：完全不消费随机流，且列表变长时既有元素的相对序不变。

### 字节锚结果（`--step 1a-ii`，基线＝1a-i′ 后的池）

**结构上无字节锚**——`_select_fragment_templates` 改了选型 ⇒ 片段身份全变
（`fragments` 340 → 352，保留键率 **0.3765**）。能保的只有它之前生成的三张表：

| 结果 | 内容 |
|---|---|
| **PASS** | `world.buildings.core` / `world.components` / `world.locations` / `world.meta` 逐字节相同 |
| 允许改变 | 其余 19 个单元（含 `fragments` 340→352、`measurements` 6,105→6,285、`sidecar_entries` 19,090→19,642） |

### 🔴 一处对核清的订正：`buildings` 表**不是**整表不变

核清 §4.2 写「`build_components` / `build_locations` 在 `_select_fragment_templates` 之前
⇒ `buildings` / `components` / `locations` 三张表仍逐字节相同」。**对 `buildings` 只有 16 列成立**：
第 17 列 `derived_outcomes_json` 是 `populate_derived_flags` **事后回写**的
（A 类综合派生 flag 汇总，读 conditions/measurements），实测 1a-ii 下差 **24/50 栋**。
⇒ 验证器把 `world.buildings` 拆成 `.core` ／ `.derived_outcomes` 两个单元。
不拆的话，这条正当的 allowed-change 会被记成**锚失败**——
而「锚失败」在本案里是要停下来查的信号，误报一次就会浪费一轮。

### 测试

- **T1**：断言 `_select_fragment_templates` 签名里**没有** `rng`，且按位置传 rng 会 `TypeError`

- **T3 插入稳定性属性测试**：200 个 world_id，注册表追加一张模板 ⇒
