## 一、宏观：满血版 vs evo 探索版 + 为什么加限制

1. **满血版（固定不动）vs evo 探索版（我们实验的）**：满血版 = 完成阶段一合规报告那个 agent，是**资源充足下的质量天花板**（family_recall=1.0）。evo 探索版 = 我们做 skills 实验的版本。**不混用，满血版代码不碰。**

2. **为什么满血版做好了还要 evo + 加限制**（用户校验的宏观）：满血版证明"给够资源 agent 能做对"；但真实部署/规模化资源受限（海量楼 × 慢 × token 成本），不可能每栋暴力穷举。**evo + skills = 受限资源下用经验逼近天花板（更少资源 = 同等质量 = 可规模化）。加限制 = 模拟资源受限、让经验价值显现** —— 无限制谁都做满、看不出 skill；加限制才证 skill 价值。呼应「Scaling Law 延伸到运行阶段」。

3. **加限制的双重作用**（用户纠正我对"0 candidate"的误解）：① 制造场景让 skill 发挥；② **让 induction 有失败模式可学** —— 无约束时 agent 做满、没重复失败 → induction 0 candidate（学不出 skill）。**正因为无约束学不出，才开 evo 探索版加难度** → 约束下 agent 系统性失败 → 聚焦重复的失败模式 → induction 才学得出 skill。**「以前那套 induction（满血 trace、0 candidate）」≠「evo 加难度」，是两回事。**

4. **evo 探索版现在还没 spec、不受 spec 制约**（已存记忆 `feedback_evo_no_spec_constraint`）：spec 制约只适用 W0/W1/W2 + 满血版；探索版机制设计（skill 注入 / partition-to-front / 闭包预算等）自由，**别拿满血版的 spec 去卡探索版**。

## 二、agent 机制

5. **agent = 带工具箱的自主 ReAct**：读建筑信息 / 法规卡 / 法规原文 / 跑闭包 等都是 **agent 可选的工具调用**（自主决定调哪个、何时调），不是写死的流程步骤。

6. **agent 不判违规，只做尽量完整的闭包核验**；**W2 是"完整闭包结果"的参考真值**，不是"是否违规"标签。推理 blind（不碰 W2），W2 只在学习/评测看。

7. **skill 触发是在环的**：每轮根据情况自动触发给 agent，不是只触发一次。

8. **法规侧 = rule-skills-kg-rag**：skill 是嵌入 KG-RAG 的节点、跟 rule cards 有机结合（`CHAIN_HAS_SKILL` 边）。**学习阶段（induction 学 skill 嵌入 KG）+ 使用阶段（检索触发）要配套。**

## 三、★ EXP-008 核心机制（我反复错、用户反复纠正）

9. **两个轮数分清**：① **完整工具调用轮数**（`max_tool_iterations`，含 retrieve/run_closure/finalize，关报告完整性，**不动**）；② **闭包查询轮数**（动这个）。

10. **★★ 闭包阻碍加在 `run_closure`（分批闭包），不是 `query_open`（读取）** —— 最关键的纠正：
    - 现在 `run_closure_verification` 一次把所有家族/规则喂进去 → 一次全判（825 obligations）= **无阻碍**，所以 family_recall=1.0、skill 没空间。
    - **正确：agent 多轮调 `run_closure`，每轮只对它选的家族子集跑闭包（一次不返回全部），逐步查清哪些家族能闭包**；阻碍 = 限总轮数 / 总能闭包的家族数。
    - 这样 **closure 只覆盖 agent 查过的家族 → family_recall（覆盖 vs W2）直接受 agent 选择影响 → skill 帮优先查关键家族 → 预算内 family_recall 更高 → skill 价值就落在 family_recall（closure metric）上**。
    - **翻页 = 分批返回闭包结果（不一次全返回），由 agent 决定多轮怎么逐步查清哪些能闭包。**
    - 这是夜间 paging 雏形「每轮查一个家族闭包」的**正确版**（去掉偷看 W2 的错、改用"closure 实际覆盖了哪些家族"算 recall）。

11. **EXP-008 验证目标不变**（用户纠正"不是定位改变"）：验证的是「skill 在闭包查询预算约束下，能否帮 agent 用更少轮 / 更聚焦达到同样的核验质量（family_recall）」。只是**技术实现要补 skill 注入 + 分批闭包的代码**。

12. **skill 注入现状**（我摸清的）：`skill_runtime`（load/match）+ `rule_retriever.apply_skill_aware_ranking` 写好 + 单测过，但**从没接进 agent 主路径**（RunOrchestrator / retrieve_rule_slice 都不调）→ skill 零作用。要 monkey-patch 接通（不改 src）。
