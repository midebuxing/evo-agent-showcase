## 根因溯源：确定性档"从不自信判 fail"是设计、不是 bug——"判对"指标从根错配（2026-07-09）

追"确定性档 agent 结构上从不判 fail"的来历（双子代理查 spec 蓝图汇总/ + pro round-3 原件）。

### 来历：保守副驾驶是 spec/pro 明文有意设计
- **spec §1.0 原则1**："只输出闭包验证情况 + 辅助审查报告，**不输出最终合规裁决**"——确定性档明确定义为**人工审查员副驾驶**，判"合不合格"不是它的活。
- **spec §D-004「闭包状态与满足性状态分离」**：`closure_status(closed/open/blocked)` 与 `satisfaction_status(satisfied/violated/unknown/na)` 刻意拆为两轴；`closed+violated`→**allow_stop=true 但交人工复审**。即"能不能停"⊥"合不合格"。
- **§6.5.1**："violated_count>0 不会自动导致 allow_stop=false"（三轮 v0.2/v0.3/round1 逐字一致）。
- **保守姿态**：pro 明文贯穿四层（状态语义/义务推导 §6.3.10.4 不得默认 satisfied/合并取最保守/报告话术），理据=确定性底线防幻觉 + 副驾驶。
- **盲不对称**：agent 盲侧闭包（§6.1 forbidden input）；W2 是生成侧答案钥匙（`regulation_projection_executor._derive_expected_verdict` 取埋入真值），敢自信投 fail=blind 红线本身。
- 原产地：pro round-3 输出 `杂物箱/文件包/…proagent_round3/…v0.3_final.md`，原样进权威 spec v0.4、逐字落码。

### 两个诚实补丁
1. **"正交"是我们的词、非 pro**——pro 原词"拆为两轴/分离"。
2. **"unknown 盖过 fail"这条 pro 写了规则、没论证、没预见后果**：§8.3.1 归约码（open/blocked→unknown 排在 violated→fail 前）pro 逐字写了，但**通篇无一句解释为何 unknown 压 fail、也没预见"族里有 violated 时被 unknown 抹掉"**。→ "pro 论证过的有意设计"只对**保守副驾驶大框**成立，对**unknown 盖 fail 具体机制**不成立（是写下的规则 + 未预见副作用）。

### 关键区分：盖住 fail 在阅卷侧、不在产品
**产品（闭包验证器）正确暴露 violated**——allow_stop=true + violated 标记待人工复审（D-004），副驾驶该做的做了。是**阅卷侧 family 归约（§8.3.1，mapper.py，eval 用）**把 agent 丰富的义务输出压成单一 family verdict、丢进 unknown，再拿去比 W2 自信裁决——**"判对≈2"是这一步造的指标假象**。
- **张力**：D-004 想让 `closed+violated` 浮出来交人工，§8.3.1 归约却把它盖回 unknown（有 open/blocked 兄弟时）。二者打架，且盖住这步只在 eval 侧、**不碰判定权红线**（allow_stop/闭包态仍由确定性验证器出）。

### 结论
**拿"判对"（agent family verdict vs W2 自信裁决）衡量这个保守副驾驶从根错配**——拿"请人复审"比"不合格"，本就不该对上。错配里唯一"非设计、可议"的点=eval 侧 §8.3.1 让 unknown 盖掉**已闭合的 violated**。→ **下一步：重想确定性档该用什么指标**（候选：allow_stop 正确性 / violated-recall 即真值 fail 时 agent 有没有正确标出疑似违反 / 闭包覆盖完整性 / blind-recall），而非在"判对"上 grind。EXP-012"提判对"主线据此该重定。
